# RBAC 实施计划

> **⚠️ 本文档是早期规划，两处原则已被后续实现推翻（2026-10-22）。**
>
> 1. **"不使用隐式超级管理员"已不成立。** 现在与 RuoYi-Vue-Plus 一致：`userId == 1` 即超管，注入 `superadmin` 角色与 `*:*:*` 通配权限，账号不可改/删/停用。
> 2. **"每次授权实时加载"已不成立。** 权限改为登录时快照写入会话，鉴权只读上下文；权限变更后通过 `revokeUserSessions` 踢人。
> 3. **"最后一位管理员"保护已移除。** 只保留超管不可操作这一层。
>
> 当前实现以 `docs/rbac-compare-ruoyi-plus.md` 为准。下文作为历史决策记录保留。

## 1. 目标与边界

在不修改 Prisma 字段、关联、索引或数据库迁移的前提下，为 gateway 建立可执行的认证、功能权限和数据范围控制，并提供维护用户、角色、菜单及部门关联的系统管理接口。允许使用不改变数据库结构的 Prisma model 指令（例如 `@updatedAt`）。实现按当前 NestJS 模块组织方式落地，system 下的业务模块参考 `apps/gateway/src/modules/system/example`。

本计划以仓库当前内容和已确认的设计方向为依据：按现有表结构与常见 RBAC 设计实施，认证采用 Access JWT + Redis Refresh Token。后续若出现新的协议或兼容要求，再按实际材料调整对应接口约定；不因此改变 Prisma 表结构。

## 2. 当前项目基线

- `prisma/models/user.prisma`：`User` 包含账号、密码哈希、状态、删除标志、部门和登录审计字段；通过 `UserRole` 多对多关联角色。
- `prisma/models/role.prisma`：`Role` 包含 `roleKey`、状态、删除标志和 `dataScope`；通过 `RoleMenu`、`RoleDept` 关联菜单和自定义数据部门。
- `prisma/models/menu.prisma`：`Menu` 可表示目录（`M`）、菜单（`C`）和按钮（`F`），`perms` 用于操作权限标识。
- `prisma/models/dept.prisma`：部门具有 `parentId` 与含自身的 `ancestors` 路径，可供部门树及下级范围计算使用。
- `prisma/models/relations.prisma`：已有用户-角色、角色-菜单、角色-部门关联表，复合主键和级联删除均已定义。
- `libs/auth` 与 `libs/permission` 已接入 JWT/会话、认证守卫及角色/菜单权限查询；当前角色权限加载不缓存。
- `apps/gateway/src/modules/system/system.module.ts` 当前全局导入 `ExampleModule`。示例展示 controller/service/module/dto 的目录和 ESM `.js` 导入约定。
- `DatabaseModule` 全局提供 `PrismaService`；`CacheModule` 全局提供 Redis 能力；`CryptoModule` 和 `CoreModule` 注册全局守卫、异常过滤器与响应拦截器。
- 阶段 1 已新增唯一 JWT 直接依赖 `@nestjs/jwt`；`libs/crypto` 提供 Argon2id 密码哈希服务。

## 3. 设计原则

1. 数据库结构保持不变。只使用现有模型及关联表，不运行 `prisma migrate` 或 `db push`；可调整不改变数据库结构的 Prisma model 指令。实现阶段通过生成客户端验证当前 schema 与代码所需 API 一致。
2. 区分认证与授权。认证确认请求者身份并构造可信用户上下文；功能授权根据菜单权限标识判定；数据授权根据角色 `dataScope` 生成业务查询约束。
3. 服务端鉴权为准。前端路由和按钮权限由接口返回以控制展示，但不能代替 API 守卫或业务查询的数据过滤。
4. 默认最小权限。未标注公开或所需权限的受保护接口拒绝未认证请求；无权限元数据的认证接口不应被意外当成公开接口。
5. 登录态与权限变化可控。角色、菜单、账号状态变化后，应在下一次受保护请求或刷新令牌时生效；不得只依赖长期有效且携带过期权限快照的 JWT。
6. BigInt ID 在 HTTP JSON 中统一使用十进制字符串输入和输出；不得直接序列化原生 BigInt。

## 4. 模块职责建议

### 4.1 Gateway `system` 业务模块

在 `apps/gateway/src/modules/system` 创建并注册以下业务模块。目录内部沿用示例的 `*.module.ts`、`*.controller.ts`、`*.service.ts`、`dto/` 布局；Prisma 操作留在 service 层。

| 模块   | 职责                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `auth` | 登录、刷新、退出、当前用户信息、当前用户可用路由/菜单权限查询；依赖 `@app/auth` 与 `@app/permission`。                         |
| `user` | 用户查询、创建/更新、状态与逻辑删除、分配角色；只通过现有 `User`、`UserRole`、`Dept` 关系操作。                                |
| `role` | 角色查询、创建/更新、状态与逻辑删除、分配菜单、维护 `dataScope` 及自定义部门范围；只通过 `Role`、`RoleMenu`、`RoleDept` 操作。 |
| `menu` | 菜单/按钮树查询及维护，确保 `menuType`、父子结构、`perms` 与角色关联可管理。                                                   |
| `dept` | 部门树查询及维护，为用户所属部门和数据范围提供基础数据；维护既有 `parentId`、`ancestors` 语义。                                |

`system.module.ts` 导入这些业务模块。是否保留 `ExampleModule` 以及上线时是否移除示例接口，在实施阶段按项目现状单独决定，不作为 RBAC 改动的隐含清理。

### 4.2 `libs/auth` 认证库

负责认证领域的可复用能力：令牌签发和验证、公开接口/当前用户元数据、认证守卫、认证用户上下文类型、会话刷新与撤销。建议导出 `AuthModule`、`AuthService`、认证守卫和装饰器/类型，避免将登录流程写进全局守卫。

认证采用 `@nestjs/jwt` 签发/验证短时 Access JWT，以及 Redis 中可撤销/轮换的 Refresh Token。JWT 仅承载稳定的 `sub`（用户 ID）及必要的会话标识，不把角色权限作为长期可信来源。Refresh Token 保存 SHA-256 摘要，刷新时原子轮换并拒绝重放；登出撤销对应会话。具体算法、claims、有效期与多设备规则以阶段 0 决策为准，配置入口见阶段 1 基线文档。

登录时按 `userName` 读取用户，检查状态和 `delFlag`，用 `PasswordHashService` 验证 `password`；成功后更新现有 `loginIp`、`loginDate` 字段并签发令牌。认证守卫对每个受保护请求验证令牌，再根据 `sub` 重新加载有效用户状态并构造 `request.user`。不能把密码哈希、删除用户或禁用用户作为有效登录主体。

### 4.3 `libs/permission` 授权库

负责授权元数据和判定，不处理登录密码或令牌生命周期。提供权限声明装饰器、公开接口元数据（或由 auth 库统一提供）、功能权限守卫、当前用户权限查询，以及数据范围解析能力。

功能权限以 `Menu.perms` 为授权标识，角色经 `UserRole` -> `RoleMenu` -> `Menu` 获得权限。仅启用且未逻辑删除的用户、角色、菜单参与计算。一个用户的多个有效角色采用权限并集；用户没有可用角色/权限时默认拒绝受保护的功能权限。对超级管理员的特殊放行若确有需要，必须用明确、可审计的既有角色/账号约定实现，不通过隐藏的任意 ID 判断。

## 5. 数据范围语义

根据 `Role.dataScope` 注释保留六种范围，不增加数据库字段。每个需要数据隔离的业务查询必须显式应用数据范围过滤；权限库提供可组合的解析结果，由业务 service 将它合入查询条件。

| `dataScope`          | 处理建议                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------- |
| `1` 全部             | 不添加部门/用户范围限制。                                                                    |
| `2` 自定义           | 只包含该角色 `RoleDept` 明确指定的部门，不自动包含下级。                                     |
| `3` 本部门           | 只匹配当前用户的 `deptId`。                                                                  |
| `4` 本部门及以下     | 匹配当前部门及其后代；优先使用 `Dept.ancestors`，并针对实际路径格式和边界匹配编写测试。      |
| `5` 本人             | 只匹配当前用户 ID。                                                                          |
| `6` 部门及以下或本人 | 匹配当前部门及其后代，或本人创建/拥有的数据；具体业务字段（如 `createBy`）按模型逐模块定义。 |

多角色范围合并按并集处理：任一有效角色为 `1` 时为全部范围；其余角色分别解析后取并集。`deptId` 为空、无效范围码、部门已删除或自定义部门为空时采取拒绝/空结果策略，不能意外退化为全量访问。实现前核对各业务表的部门归属字段；当前 schema 仅明确 User/Dept 等结构，并未证明每个业务模型都有相同的归属字段。

## 6. 分阶段实施

### 阶段 0：确认接口约定与边界（已完成）

1. 将本计划确定的认证、角色权限和数据范围语义整理为接口约定，标明登录响应、权限码及菜单路由字段。
2. 确定 Access/Refresh Token 有效期、是否允许多设备会话及登出范围；Refresh Token 采用轮换和服务端撤销。
3. 按现有表语义确定 `dataScope=2` 使用 `RoleDept` 关联的部门集合；是否将部门下级纳入范围、数据范围应用到哪些业务实体，在接入对应模块时逐项确认。
4. 如后续需要兼容特定前端协议，再将路径、响应 DTO 和路由字段映射到现有 `Menu` 字段，不增加数据库字段。

**验收：** 认证方案、接口基线和数据库不变更约束已确定；依赖具体业务模型的字段已标记为接入该模型时落实。

### 阶段 0 决策记录（2026-10-22）

| 主题       | 已确定的基线                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 认证形式   | Access JWT 使用 HS256，要求至少 256 位随机密钥，有效期 15 分钟，并校验 issuer、audience、`iat`、`exp`。Refresh Token 使用 256 位密码学安全随机值，不使用 JWT，服务端只保存 SHA-256 摘要。Refresh Token 有效期 7 天，按绝对期限计算，刷新时轮换且不延长会话期限。                                                                                                                                                                                                      |
| 会话与撤销 | 每次登录创建独立会话，允许同一用户多设备登录。Redis 保存会话状态和当前 Refresh Token 摘要；Access JWT 带 `sub`、`sid`、`jti`、`iat`、`exp`，认证守卫同时确认 JWT 有效、Redis 会话仍有效、数据库用户仍启用。刷新需原子消费当前 Refresh Token 并换发；已消费令牌重放时撤销该会话。Redis 会话操作不可用时认证/刷新失败关闭并返回服务不可用。登出撤销当前 `sid`，并使该会话的 Access Token 立即失效；其他设备会话不受影响。                                               |
| 权限生效   | JWT 不携带角色权限作为授权依据。每个受保护请求按 `sub` 读取当前用户及有效角色/菜单权限，确保禁用用户、角色菜单变更即时生效；未做出明确失效机制前不缓存权限结果。                                                                                                                                                                                                                                                                                                      |
| 角色与权限 | 多个有效角色的功能权限取并集。功能权限码精确匹配 `Menu.perms`；目录/菜单（`M`/`C`）用于路由树，按钮（`F`）用于权限码。登录用户没有所需权限时拒绝访问。不存在隐式超级管理员 ID 或角色绕过；管理员通过明确分配的角色与菜单权限获得管理能力。                                                                                                                                                                                                                            |
| 数据范围   | 多个角色的数据范围取并集，任一有效角色为 `1` 即全量。`2` 仅包含关联表 `RoleDept` 明确指定的部门，不自动扩展下级；`3` 为当前部门；`4` 为当前部门及下级；`5` 为当前用户创建/拥有的数据；`6` 为当前部门及下级的数据并集当前用户创建/拥有的数据。`4`/`6` 使用 `Dept.ancestors`，编码时按其实际路径格式实现安全边界匹配。每种业务记录的“创建/拥有”字段按对应 Prisma model 确认，没有可用字段时拒绝或不开放该范围，不能漏掉过滤。                                           |
| 状态字段   | 以现有数据约定为准；按当前默认值，用户/角色/菜单/部门 `status='0'` 表示正常可用，非 `'0'` 不参与认证/授权；用户/角色 `delFlag='0'` 表示未删除，非 `'0'` 不参与认证/授权。实现阶段需用生产/开发既有数据核验这些取值。                                                                                                                                                                                                                                                  |
| HTTP 接口  | 公开接口仅限登录、刷新和健康检查，并必须显式标记。其余接口默认需认证；需要功能权限的接口显式声明权限码，无权限元数据的管理写接口拒绝访问。认证端点采用 `/auth/login`、`/auth/refresh`、`/auth/logout`、`/auth/profile`、`/auth/menus`；资源管理使用 `/system/users`、`/system/roles`、`/system/menus`、`/system/depts`。登录请求提交 `userName`、`password`；刷新请求在 JSON body 提交 `refreshToken`；登出使用当前 Access Token。路径最终以 Nest 全局 API 前缀为根。 |
| 响应与标识 | 遵循现有响应包装：成功 `{ code: 0, data, message }`，失败使用既有错误格式，未认证 HTTP 401、无权限 HTTP 403。登录 `data` 返回 `accessToken`、`refreshToken`、`tokenType: "Bearer"`、`expiresIn`（秒）和脱敏 `user`；菜单和权限通过独立接口返回。所有 BigInt ID 在 JSON 中使用十进制字符串。                                                                                                                                                                           |
| 客户端约定 | 当前仓库没有前端登录 API/DTO 可兼容；先以以上后端协议为基线。菜单路由树只从现有 `Menu` 字段组装，按钮权限返回 `perms` 字符串集合；不假设表中有 `name`、`redirect` 等未定义字段。客户端若需额外显示元数据，先由接口映射/组装，不改 schema。                                                                                                                                                                                                                            |
| 配置与安全 | JWT 签名密钥、算法和上述有效期通过新的 auth 配置域接入现有配置加载/校验；密钥只来自不入库环境配置或密钥挂载。Redis 用既有 `RedisService` 严格操作，不自行创建第二个连接。密码沿用 `PasswordHashService` 的 Argon2id。                                                                                                                                                                                                                                                 |
| 初始化约定 | 不自动授予隐式管理员权限。初始管理员、角色、菜单通过一次性受控初始化脚本或既有数据导入创建；脚本不得新增表/列，也不得将默认凭据写入仓库。                                                                                                                                                                                                                                                                                                                             |

上述有效期和状态值是本次确认的实施基线；上线前仍需核验目标环境的现存数据、秘钥注入方式和业务实体的数据归属字段，不再作为阶段 0 的阻塞项。

4. 盘点系统接口的 ID 与分页 DTO 约定，确定 BigInt 的传输/序列化方式。

### 阶段 2：建立认证与权限库基础（已完成）

1. 在 `libs/auth` 实现认证上下文类型、JWT 适配、公开接口元数据、认证守卫和服务接口；在 `libs/permission` 实现权限声明元数据、功能守卫和权限服务接口。
2. 以 Nest `Reflector` 读取 handler/class 元数据：`Public` 方法配置覆盖类配置；权限与角色要求跨类/方法、跨注解固定 AND，单条注解内由 `mode` 控制 AND/OR（默认 AND），`role` 仅兜底当前权限注解。
   同步接入当前尚缺少的全局 DTO 校验管道，校验失败沿用现有 422 字段错误结构。
3. 按全局守卫顺序接入认证与授权：公开接口跳过认证；其余请求先认证，再授权。核对 `CryptoModule`、`CoreModule` 的现有 `APP_GUARD`，确保 guard 顺序可预测，异常经过现有异常过滤器。
4. 为登录、刷新、退出和获取当前用户信息定义 DTO 与统一响应。Refresh Token 放入 Redis 的键空间、TTL、轮换和撤销机制写出明确语义。
5. 编写守卫与令牌单元测试：缺失/无效/过期令牌、公开路由、禁用/删除用户、刷新轮换、退出撤销和令牌重放。

**验收：** 守卫能在隔离测试中稳定区分公开、未认证、已认证及无权访问；测试不依赖真实数据库或 Redis。

已在 `AppModule` 直接导入认证/权限模块并按序注册两个全局守卫，无单独的 AccessControlModule；已交付认证/权限/角色装饰器、JWT 与 Redis 会话服务、认证 DTO 和全局 422 校验。接口、会话协议、测试方式及阶段边界见 [阶段 2 说明](./rbac-phase2-auth-foundation.md)。

### 阶段 3：实现用户权限加载和功能授权（已完成）

1. 通过 `PrismaService` 查询当前有效用户和关联角色，不信任客户端传入的 userId、roleId 或权限列表。
2. 解析角色关联菜单，忽略失效角色/菜单，聚合 `perms`；权限查询可用于守卫检查和当前用户信息接口。
3. 设计失效策略：角色、角色菜单、用户角色、菜单状态变化后，权限数据必须按约定及时生效。优先在请求中以用户 ID 重新校验或采用有明确失效机制的短期缓存，不能无失效地缓存权限快照。
4. 给关键接口声明所需权限码，统一格式并用 DTO/接口文档展示；缺少必要权限的敏感写操作按拒绝处理。
5. 测试多角色并集、无角色、失效角色、菜单禁用、菜单/按钮权限码匹配和管理员特殊策略（若已确认）。

**验收：** 请求只有在其用户当前有效角色拥有对应 `Menu.perms` 时才可通过；前端返回的权限不参与服务端决策。

阶段 3 已通过 `PrismaPermissionSource` 按可信用户 ID 查询有效角色与菜单权限，每次授权实时加载且失败关闭。无效用户返回 401、查询故障返回 503；停用/删除角色和停用菜单会即时移除权限。不使用隐式超级管理员，全部边界与验证见 [阶段 3 权限加载说明](./rbac-phase3-permission-loading.md)。登录及当前用户业务 HTTP API 留在阶段 4。

### 阶段 4：实现认证业务接口（已完成）

1. 创建 `apps/gateway/src/modules/system/auth`，实现登录、刷新、退出、当前用户（如 `/auth/profile`）及路由/菜单权限查询接口。
2. 登录响应仅返回约定的用户基本信息、令牌和有效权限展示数据，不返回密码哈希或内部敏感字段；更新 `loginIp`、`loginDate`。
3. 刷新操作验证并轮换 Refresh Token；退出撤销当前会话。失败响应统一使用 `BusinessException`/现有错误体，不泄露账号是否存在或密码是否错误。
4. 将模块加入 `SystemModule`，在 Swagger 中为 DTO、认证头、返回值生成准确文档。
5. 测试完整登录、刷新、退出及当前用户查询流程，使用 Prisma/Redis mock 或专用集成测试依赖。

**验收：** 未登录访问受保护接口返回统一 401；有效登录后可查询本人上下文；退出或刷新后旧会话令牌按策略失效。

已在 `SystemModule` 注册认证业务模块，交付登录、刷新、退出、本人资料和菜单树五个端点；复用既有 JWT/Redis 会话与实时权限查询。账号歧义拒绝、统一错误、脱敏、登录审计、菜单树边界、Swagger 和验证方式见[阶段 4 接口说明](./rbac-phase4-auth-api.md)。正常刷新仅消费旧 Refresh Token；旧 Access Token 仍可使用至到期，重放或登出则撤销该设备全部令牌，其他设备不受影响。

### 阶段 5：实现 RBAC 管理 API（已完成）

1. 建立 system 下 `user`、`role`、`menu`、`dept` 模块，文件布局和 DTO 风格参照 `example`。
2. 用户服务负责用户基本资料、状态、逻辑删除、部门和角色关联；角色服务负责角色基本资料、状态、逻辑删除、菜单关联、数据范围和自定义部门关联。
3. 菜单服务管理目录/菜单/按钮树、父子关系、路由展示字段和 `perms`；部门服务管理树、`ancestors` 维护和用户部门引用约束。
4. 对关联替换使用 Prisma transaction，验证输入 ID 均存在且有效；逻辑删除前检查引用和管理员保护规则。账号名/角色标识无唯一约束，按阶段 1 基线在 Serializable 事务内查重并处理并发冲突；关系表的重复关联由现有复合主键约束处理。
5. 用明确的 `system:user:*`、`system:role:*`、`system:menu:*`、`system:dept:*` 权限码保护管理接口；读写权限分离。
6. 仅实现 RBAC 必需的管理字段和操作，不扩展与当前 schema 不匹配的权限实体。

**验收：** 可创建和维护用户/角色/菜单/部门关联，关联更新具备事务性；所有管理 API 受认证和权限守卫保护。

四个管理模块已接入 `SystemModule`，接口、字段映射、引用和管理员保护规则及验证见[阶段 5 管理 API 说明](./rbac-phase5-admin-api.md)。

管理列表直接将 `this.prisma.user` / `this.prisma.role` 传给 `paginate(this.prisma.<model>, { ...query, where })`；关联集合在分页后单独查询。公共树组装导出自 `libs/common/src/utils`。响应统一经 `toDto`、`toDtoList` 或 `toPageDto` 映射到逐字段 `@Expose()` 的 DTO，BigInt ID 使用 `@Type(() => String)`，日期使用 `@DateFormat()`；业务模块内不再设置共享 RBAC 服务目录或通用资源/响应包装方法。

### 阶段 6：落实数据范围到业务查询（已完成）

1. 在 `libs/permission` 提供数据范围解析器，输入当前用户及有效角色，输出业务查询可组合的用户 ID/部门 ID 条件或等价的受限谓词。
2. 为需要隔离的数据列表、详情、更新、删除接口逐个接入条件；写操作必须同时验证目标记录在当前范围内，避免只过滤列表。
3. 实现六种范围、角色并集、自定义部门和祖先路径解析；空部门和未知范围一律产生空授权或明确业务错误。
4. 为每个接入的数据模型记录范围字段，例如部门归属字段、创建人字段；某模型没有可用字段时先定义安全策略，不可静默跳过过滤。
5. 为范围边界编写测试：本部门/子部门/其他部门/本人/他人、多个角色、无部门用户及自定义部门。

**验收：** 相同接口对不同数据范围用户返回和修改的数据严格受限，直接通过 ID 访问不能绕过范围条件。

阶段 6 已交付 `libs/permission/src/data-scope.ts`（`resolveDataScope` / `loadDataScope` / `withDataScope` / `isDeptInScope`），并在用户、部门、角色的部门树查询中接入。与 Java 的差异（写操作使用并集而非 AND、数据范围不进会话快照、角色列表因缺 `create_dept` 列未接入）见[阶段 6 数据范围说明](./rbac-phase6-data-scope.md)。

### 阶段 7：全链路验证、文档与交付

1. 运行 `pnpm exec prisma generate`（只生成客户端，不改 schema）、`pnpm build`、`pnpm test` 及相关 e2e；如项目既有问题影响结果，区分基线失败与本次失败。
2. e2e 覆盖登录、权限允许/拒绝、Refresh Token 轮换与撤销、用户/角色授权变更后生效、数据范围读写隔离、逻辑删除和统一错误响应。
3. 检查 `git diff -- prisma` 为空，确认没有迁移文件或 schema 变化；检查启动配置无真实密钥。
4. 更新 Swagger/API 文档及部署配置说明，给出初始管理员与角色/菜单初始化的安全操作方式。由于数据库不能改结构，初始化数据只能以受控脚本/既有数据导入方式提供，不得假设新增 seed 表或列。
5. 输出模块结构、接口清单、权限码清单、配置项、验证结果和未解决决策。

**验收：** 构建和相关测试通过；数据库结构零变更；核心认证、功能授权与数据范围行为均有自动化覆盖和操作说明。

## 7. 建议接口清单（待与客户端协议约定）

| 方法                    | 路径（位于全局 API 前缀下）                                        | 目的                                                        |
| ----------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------- |
| `POST`                  | `/auth/login`                                                      | 账号密码登录并建立会话。                                    |
| `POST`                  | `/auth/refresh`                                                    | 轮换 Access/Refresh Token。                                 |
| `POST`                  | `/auth/logout`                                                     | 撤销当前会话。                                              |
| `GET`                   | `/auth/profile`                                                    | 返回当前用户与角色/权限摘要。                               |
| `GET`                   | `/auth/menus`                                                      | 返回当前用户可见的菜单/路由树。                             |
| `GET/POST/PATCH/DELETE` | `/system/users`、`/system/roles`、`/system/menus`、`/system/depts` | 对应资源的查询与维护；最终路径遵循现有 API 命名和分页约定。 |

公开接口必须显式声明；除登录/刷新及健康检查等确需匿名访问的端点外，不得默认开放管理 API。

## 8. 实施时需落实的项目约定

- 按阶段 0 的有效期、多设备及登出范围实现；auth 配置域已接入，部署时必须提供本地或挂载密钥。
- `dataScope=2` 只包含选定部门；`dataScope=6` 中“本人”对应的创建人或业务所有者字段，按具体业务模型定义。
- 前端登录响应、菜单路由字段和权限码格式；Prisma `Menu` 有字段限制，需映射现有字段或在接口层组装，不能假定表中已有额外元数据。
- 管理员通过显式角色菜单授权，不做超级管理员绕过；管理员保护操作在管理接口中落实。
- 现有数据库中的状态字段取值，以及初始管理员、角色、菜单数据的安全初始化方式。
