## 1. 结论与适用范围

项目目前有一个网关应用、一个用户业务模块和八个基础库。排除 Prisma 生成代码后，`apps`、`libs`、`test` 下共 77 个非测试 TypeScript 文件（约 2927 行）、10 个测试文件（约 1074 行）。业务 CRUD 大多仍为占位实现，当前不适合抽象通用 Controller、Service 或 Repository 基类。

值得优先处理的是**同一规则存在多个维护位置**：日期格式化、配置整数解析、分页常量、API 加密支持的方法。这些规则已经出现行为或契约分歧。重复的字段声明、测试辅助代码和工具配置应随后处理。

首次审查仅新增本文档；后续 P1 实施状态见第 8 节。实际执行改造前应再次核对工作区，保留已有修改。

审查范围：网关启动与用户模块，common/config/core/crypto/database/cache/logger/swagger，Prisma 模型，测试与构建配置，根 README 和 Crypto README。排除 `node_modules`、`dist`、日志、锁文件和 `libs/database/src/generated/prisma`；生成代码的重复不应手动治理。

方法：阅读源码、搜索调用与规则定义、对照已有测试，并执行类型检查、部分端到端测试和只读 ESLint。本文没有运行克隆检测工具，不给出未经测量的“重复率”。

## 2. 优先级与总览

## 4. 各项修改步骤与验收

### D01：日期格式化只保留一份实现

**位置：** `libs/core/src/decorators/date-format.decorator.ts:12-38`。

`DateFormat()` 的 Transform 回调与 `formatDateValue()` 对空值、Date、字符串、无效日期和时区格式化的逻辑重复。以后调整格式或时区时有漏改风险。

步骤：

1. 为现有纯函数和装饰器补充等价性用例，覆盖 null/undefined、有效和无效 Date、有效和无效日期字符串、数字、自定义格式。
2. 让装饰器直接调用已有函数，只删除因委托而重复的算法主体。
3. 保持函数名、导出、默认格式、时区和 Transform 执行方向不变；不顺便将转换改成 `toPlainOnly`。

目标形态：

```ts
export function DateFormat(format: string = DEFAULT_DATE_FORMAT): PropertyDecorator {
  return Transform(({ value }: TransformFnParams) => formatDateValue(value, format));
}
```

验收：同一输入通过函数和装饰器得到相同结果；现有序列化行为不变。不要仅测试“函数被调用”，应断言输出值。

### D02：合并配置整数解析的公共部分

**位置：** `libs/config/src/core/parsers.ts:50-61`，三个域包装函数见总览表。`app.domain.ts:19`、`database.domain.ts:37-44` 还直接使用宽松解析。

现有行为并不相同：

| 输入/规则 | `asInteger` | logger 包装 | throttler 包装 | Redis 包装 |
| --- | --- | --- | --- | --- |
| null/undefined | 使用 fallback，否则报错 | 同左 | 同左 | 同左 |
| 数字字符串 | 转为数字 | 允许 | 允许 | 允许 |
| `true` | 转成 1，满足 min 时接受 | 拒绝 | 拒绝 | 拒绝 |
| 空白字符串 | 转成 0，min=0 时接受 | min=1，最终拒绝 | 显式拒绝 | 显式拒绝 |
| 数组 `[1]` | 转成 1，满足 min 时接受 | 拒绝 | 拒绝 | 拒绝 |
| 安全整数和最大值 | 不检查 | 不检查 | 不检查 | 检查，且上限按字段变化 |

步骤：

1. 新增 parser 和域级表驱动测试，固定上述差异，以及浮点数、NaN、Infinity、超安全整数、最小/最大边界和带路径的报错。
2. 在 `config/core/parsers.ts` 内提取“只接收 number/非空字符串”的整数入口，复用现有转换；必要时只增加 max 参数。域内继续决定 min/max/fallback，不引入 schema 引擎。
3. 先替换 Redis、throttler、logger 三个包装函数。Redis 的安全整数和字段上限不能丢，logger 的正整数错误语义需要保留或明确更新测试。
4. 单独审查 app/database 是否也改用严格入口。拒绝以前接受的 `true`、`[1]` 等属于行为收紧，应独立说明，不能作为无行为变化重构混入。
5. 删除因替换失去用途的本地包装函数和 import。

验收：三个域的既有合法配置、fallback、Redis 上限、`blockDuration=0` 等边界保持；错误带完整配置路径。只合并相同输入规则，不强制所有整数拥有同一个最大值。

### D03：分页常量只保留一个来源

**位置：** `libs/common/src/dto/base.dto.ts:16-41`、`libs/database/src/helpers/pagination.ts:23-25`。DTO 注释已明确提示必须手工保持 20/200 同步。

步骤：

1. 在 common 新建无运行时框架依赖的分页常量文件，定义现有 `DEFAULT_PAGE=1`、`DEFAULT_PAGE_SIZE=20`、`MAX_PAGE_SIZE=200`，从 common 导出。
2. PageQueryDto 的属性默认值和 `@Max()` 使用这些常量。
3. database 的分页 helper 改为引用相同常量；通过原文件或 database barrel 兼容重导出，避免破坏已有导入路径。
4. 更新“刻意不引常量”的旧注释。common 不得反向依赖 database；常量文件不得通过 DTO barrel 引入 core。

验收：原 `pagination.spec.ts` 通过；补充独立的 DTO 转换/验证用例，验证默认 1/20、边界 200、201 校验失败；`normalizePage()` 对 201 截断为 200。**保留 HTTP 严格拒绝和内部调用兜底这两种职责**，不删除任何一层校验。

此步骤不接入 QueryUserDto、不修改排序字段白名单，也不创建分页基类；这些应单独立项。

### D04：API 请求加密共享 HTTP 方法策略

**位置：** `libs/crypto/src/api-encrypt.guard.ts:31`、`libs/crypto/src/fastify-api-crypto.ts:21-24`。

Guard 决定是否要求加密头，preParsing 决定是否解密，两处各自判断 POST/PUT。如果将来只改一处，会出现“要求加密但没有解密”或策略绕过。

步骤：

1. 在 Crypto 库内部提取一个小函数（例如 `supportsEncryptedRequest(method)`），集中大写归一化和 POST/PUT 判断；不导出成跨库工具。
2. Guard 与 hook 使用同一函数，分别保留头部检查、策略选择和原有返回分支。
3. 增加 POST/PUT、GET/DELETE/PATCH、小写方法的策略用例，以及“带头解密/无头拒绝/未标记路由可传明文”的链路用例。

验收：支持方法仍只有 POST/PUT；GET 响应加密继续可用；未标记路由兼容明文。**此次不扩展 PATCH 支持**，用户更新接口虽使用 PATCH，也不能为去重顺手改变协议。

### D05：先统一响应字段契约，再复用

**位置：** `libs/common/src/dto/base.dto.ts:109-135`、`apps/gateway/src/modules/system/user/dto/response.dto.ts:5-107`、`prisma/models/user.prisma`。

四个字段重复：`createTime`、`updateBy`、`updateTime`、`remark`。但当前类型和可选性并不一致，BaseEntityDto 也尚无业务继承者，直接 `extends BaseEntityDto` 会改变输出契约。

步骤：

1. 先处理 3.3 的 ID、日期、空值和字段来源契约，建立用户响应测试。用数据库形态的数据调用 `toPageDto()` 再 `instanceToPlain()`，断言实际输出。
2. 在用户 DTO 中先修复需要暴露的日期字段；保留 password 排除测试，覆盖 BigInt ID 和 null 日期/可空字段。BigInt 转 number 必须验证安全范围，不能依赖隐式转换。
3. 核对前端与 OpenAPI。确定属性在 DTO 实例中的类型，以及转换后 JSON 类型，不能只依靠 TypeScript 声明。
4. 只有四个公共字段的契约确实一致时，才调整公共 DTO 并继承。若只有 User 一个真实消费者，优先保留显式声明，等第二个模块出现再抽取。
5. 如果选择继承，删除 User 中真正被基类覆盖的四个字段，保留用户专属字段及其装饰器。

验收：密码不输出，日期按约定输出，可空值稳定，ID 不丢精度，分页包裹不变；通过 Nest CLI 构建后核对 OpenAPI 的继承字段、格式及 required。Vitest/单独 tsc 不执行 Swagger 编译插件，不能替代文档检查。

禁止为了减少重复让创建 DTO、响应 DTO、Prisma 模型共用一个类。它们分别承担输入校验、输出白名单、持久化约束，字段相似并不代表同一职责。

### D06：缓存 TTL 复用规则，保留边界校验

**位置：** `libs/cache/src/cache.service.ts:44-47`、`libs/cache/src/redis.store.ts:28-31`，两处都限制整数毫秒 `1..2147483647`。

步骤：

1. 在 cache 内部提取 `isValidCacheTtl(number)` 或同等简单断言，集中范围规则。
2. CacheService 继续接受省略 ttl；RedisStore 继续先采用 defaultTtl 再校验。共享函数不处理 undefined，以免混淆两层契约。
3. 保留两处验证调用和各自错误提示；Store 可能被底层适配器直接使用，不能因为 Service 校验过就取消保护。

验收：省略、1、最大值成功；0、负数、浮点数、NaN、Infinity、超上限失败；关闭缓存时也按原行为校验入参。配置域里的 Redis 整数解析还处理字符串和字段路径，不与运行时 TTL 校验强行合并；跨库相同上限可先保留，避免为一个数增加依赖。

### D07：提取测试客户端协议实现

**位置：** `libs/crypto/src/api-crypto.service.spec.ts:18-45,65-73`、`test/crypto.e2e-spec.ts:44-83`。

两处重复生成 RSA 配置、构造 AES/RSA 请求；单测内联响应解密与 E2E 的 `decryptResponse` 也相似。注意请求辅助函数当前分别返回 Buffer 和 string，不能直接替换而忽略类型差异。

步骤：

1. 建立 `test/helpers/api-crypto-client.ts`，只放测试密钥工厂、请求编码、响应解码。
2. 统一编码函数返回 Base64 string；调用 `decryptRequest()` 的单测在边界用 `Buffer.from(value, 'utf8')` 转换，HTTP 测试直接使用 string。
3. 保留 shared/separate RSA 密钥对两种场景和错误输入断言。共享辅助文件不缓存跨测试的可变配置。
4. 保留至少一个不依赖共享编码辅助函数的固定协议向量或独立兼容性用例，避免所有测试共享同一个错误。

验收：单测与 E2E 都使用独立于生产 ApiCryptoService 的客户端实现；不能调用生产 `encryptResponse()` 来伪装客户端请求，也不能把生产协议代码和测试预期一并提取成同一实现。

### D08：共享测试日志读取，保留场景启动差异

**位置：** `test/app.e2e-spec.ts:92-96`、`libs/logger/src/logger.transport.spec.ts:41-47`，另外 `logger.service.spec.ts:31-33` 也手动寻找日志文件。

## 5. 应保留的结构与暂缓候选

| 结构 | 当前判断 | 建议 |
| --- | --- | --- |
| Controller → Service 的逐方法转发 | 只有 User 一个模块，且多数为脚手架占位 | 保留显式方法，不建通用 CRUD 父类 |
| User Controller 三处 `+id` | 同一转换重复，但正确类型尚未定 | 先处理 ID 契约；选 number 时可用带安全范围约束的 pipe，选 BigInt 字符串时实现匹配该契约的转换；不套用 ParseIntPipe 后默认认为安全 |
| 创建 DTO 的 `PartialType` | 已复用创建字段规则 | 保留；更新身份字段另按契约处理，不再叠加 BaseUpdateDto |
| `paginate()` 与 `toPageDto()` | 前者查询/统计，后者输出白名单与模型转换 | 保持分层，不做跨 database/common 的“一键 CRUD”包装 |
| `toDto` / `toDtoList` 的 `plainToInstance` | 共享选项已集中，单个和列表的空值策略不同 | 几行重复可保留，不为 map 再加转换器工厂 |
| 成功拦截器与异常过滤器的 `{code,data,message}` | 成功/失败职责不同，错误构造已集中在 `errorBody()` | 暂不合并，尤其不能强行让 Fastify preParsing 错误走 Nest Controller 生命周期 |
| API hook 的错误响应也有相同外壳 | 发生在请求解析前 | 新协议字段出现时再考虑 core 的纯构造函数；当前只有少量字面量，不增加跨库运行时依赖 |
| 配置域定义、类型、token、DOMAINS 注册表 | 已有 `defineConfigDomain` 和唯一域清单 | 保留显式类型与声明，不引入自动扫描注册 |
| YAML 默认值与 parser fallback | 分别是可编辑基线和缺省输入行为 | 保留，增加一致性测试比删除某一层更稳妥；环境差异层仅保留必要覆盖，但需区分显式策略和冗余 |
| HTTP 状态映射表 | `business-code.ts:70-90` 当前所有映射都等于状态本身 | P3 候选：保留函数 API、内部直接返回 status 可减少维护；但需先确认项目长期约定，不改 Prisma 错误映射 |
| 8 份库 `tsconfig.lib.json` | 模板结构相似，outDir 不同；extends/include 路径有相对解析语义 | 当前保留，不为十行配置增加共享层；若未来扩展，再通过 `tsc --showConfig` 证明每个库输入/输出路径一致 |
| `nest-cli.json` 与 `tsconfig.json` 的库注册 | Nest 构建项目和 TS 模块解析描述不同信息 | 不用脚本生成两份注册表来换取“看起来更少的重复” |
| Redis/Prisma 生命周期 | 都有 connect/disconnect，但重连、降级与失败语义不同 | 保留独立实现，不抽通用 Connection 基类 |
| AES/RSA 报文、AES-GCM 字段、Argon2 密码 | 不是同一协议 | 禁止合并成通用加密流程 |
| 测试正则集中到 core | `regex.ts` 包含多条仅为测试断言服务的规则，属于边界问题 | 不因去重继续往 core 堆测试辅助；必要时单独迁移，当前不顺手删除 |
